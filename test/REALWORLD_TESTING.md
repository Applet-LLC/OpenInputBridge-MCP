# 実機テスト記録

このドキュメントは、実際にOpenInputBridgeドライバをインストールした環境(Windows、物理キーボード複数台・マルチモニタ環境)で行った動作検証の記録です。開発環境での単体テストでは発覚しなかった、実機でしか見えないバグ・制限事項が複数見つかりました。

**環境**: OpenInputBridge 1.00 (`oib_kbd.sys`/`oib_mou.sys`, keyboardSlotCount=10既定)、Windows、日本語(JIS)キーボードレイアウト、デュアルモニタ(プライマリ 3440×1440、セカンダリ 2880×1620、仮想デスクトップ全体 4022×3780)。

## 見つかったバグ・修正

### 1. `OIB_DRIVER_IDENTITY`構造体のパッキング不一致(修正済み)

**症状**: `status`コマンドが常に`IOCTL_GET_DRIVER_IDENTITY failed`で失敗する(ドライバは実際にはインストール・稼働していたにもかかわらず)。

**原因**: [`helper/oib_bridge.c`](../helper/oib_bridge.c)側で全構造体に`#pragma pack(push, 1)`を適用していたが、ドライバ側(`driver/common/ioctl.h`)の`OIB_DRIVER_IDENTITY`は素の(自然境界)アラインメントを使用している。`ULONG×3 + BOOLEAN`の並びは、パック指定なしだと末尾のBOOLEANがパディングされ16バイトになるが、`pack(1)`だと13バイトになる。`WdfRequestRetrieveOutputBuffer`はカーネル側の`sizeof()`(16バイト)を要求サイズとして検証するため、13バイトしか用意していないクライアントは`STATUS_BUFFER_TOO_SMALL`で弾かれていた。`OIB_KEYBOARD_INPUT_DATA`/`OIB_MOUSE_INPUT_DATA`はフィールド配置上たまたまパック有無で結果が変わらず、影響を受けていなかった。

**修正**: `#pragma pack`指定を撤廃し、3構造体全てをドライバ側と同じ自然アラインメントに統一。

### 2. キーボード/マウスのスロット境界が10/10固定という誤った前提(修正済み)

`docs/PROTOCOL.md`に「10/10境界は既定値であり変更可能」と明記されていたにも関わらず、`helper/oib_bridge.c`が`OIB_MAX_KEYBOARD=10`を定数としてハードコードしていた。`IOCTL_GET_KEYBOARD_SLOT_COUNT`で都度問い合わせるよう修正(排他モード実装時に発見・修正、実機テストの前に対応済み)。

## 実機でのみ判明した制限事項

### 3. Shift状態の取りこぼし(タイミング依存、部分的に緩和・完全解決はしていない)

**症状**: `type_text`で連続してShiftキーを使う文字(例: `"MCP"`のような連続大文字)を高速に送信すると、一部の文字でShift状態が反映されず小文字になることがあった。

**原因の切り分け**:
- 各`DeviceIoControl`呼び出し自体は同期的に成功しているが、OS側の入力パイプライン(kbdclass→raw input→`TranslateMessage`/`ToUnicode`の修飾キー状態参照→`WM_CHAR`配送)は非同期に処理されるため、間隔なしに連続送信すると取りこぼしが発生する
- 同一スキャンコード(`ShiftLeft`)を短時間に連続してdown/upすると、OS側のアンチゴースト/デバウンス処理の影響を受けやすいことも確認(`ShiftLeft`/`ShiftRight`を交互に使う手動テストでは改善が見られた)

**対応**:
- `helper/oib_bridge.c`とは無関係、`src/tools.ts`側の対応: 各キー/修飾キー遷移後に最低限の間隔(`KEY_EVENT_SETTLE_MS`)を強制。`press_key`・`type_text`とも、連続する修飾キー押下では`ShiftLeft`/`ShiftRight`を交互に使用するよう変更
- 「`OpenInputBridge MCP real hardware test`」「`Second line UPPER lower`」のような、通常のテキスト(単語単位で先頭のみ大文字、または連続する大文字の並び)では、この対応後は安定して正しく送信できることを確認

**未解決の既知の制限**: `"MiXeD"`のように**1文字ごとにShift状態が切り替わる**極端なパターンでは、`delayMs`を100msまで上げても、上記対策後もなお一部の文字でShiftが反映されないことがある(`X`, `D`のような特定の文字で再現、原因は特定できず)。実際のテスト自動化で使われるテキスト(通常の英文・識別子・URL等)でこのパターンが問題になる可能性は低いと考えられるが、既知の制限として記録する。1文字ずつのcamelCase的な入力が必要な場合は、`type_text`を1文字ずつの複数回呼び出しに分割し、都度大きめの間隔を空けることを推奨。

### 4. USキー配列前提が、実際のOSキーボードレイアウトと異なると記号文字が化ける(対応済み)

**症状**: 日本語(JIS)キーボードレイアウトが有効な環境で、`type_text`に`@`や`:`、`_`を含む文字列を送ると、`@`→`"`、`:`→`+`、`_`→`=`のように異なる文字として入力された。

**原因**: `src/keycodes.ts`のスキャンコードは物理キー位置ベースで正しく送信されているが、そのスキャンコードが実際に「どの文字になるか」はOS側のアクティブなキーボードレイアウト設定に依存する。US配列を前提にした記号マッピング(`SHIFTED_DIGIT_SYMBOLS`等)は、レイアウトがUS以外の場合はズレる。

**対応(実装済み)**:
- `helper/oib_bridge.c`に`get_active_keyboard_layout`コマンドを追加。`GetForegroundWindow`→`GetWindowThreadProcessId`→`GetKeyboardLayout`で、**フォーカス中ウィンドウ**の入力ロケール(HKLの下位ワード=LANGID)を取得する(このプロセス自身のスレッドではなく、ターゲットとなるウィンドウのロケールを見る必要がある点に注意)
- `src/keycodes.ts`にJIS用の文字→キー変換表(`*_JIS`)を追加し、`charToKeyEvent(ch, layout)`で切り替え可能に。`type_text`に`layout`パラメータ(`"auto"`(既定)/`"us"`/`"jis"`)を追加、`"auto"`は呼び出しごとに`get_active_keyboard_layout`を照会して自動選択する
- JIS配列専用の物理キー5個(`IntlRo`, `IntlYen`, `Convert`, `NonConvert`, `KanaMode`、DOM `KeyboardEvent.code`準拠の命名)を`KEY_TABLE`に追加。`press_key`等はレイアウトに依存しない物理キー位置ベースなので、これらは常に(USレイアウト環境でも)利用可能

**実機検証結果**(`test/realworld_jis_layout_test.mjs`): `languageId`検出(1041=日本語を正しく検出)、数字行Shift記号(`!"#$%&'()`)、`-^=~`、`@[`{`、`]}`、`;:+*`、`,.<>?/`、`IntlRo`(`\_`)を送信し、**全て期待通りの文字が入力されることを確認**。唯一の例外として、`IntlYen`キーの無シフト時は期待した真のyen記号(U+00A5)ではなく、ASCIIバックスラッシュ(U+005C、`IntlRo`無シフトと同じ文字)が実際には入力された — これはWindowsのJIS配列ドライバの既知の仕様(Yenキーは歴史的にバックスラッシュを送出する、CP932/Shift-JISとの互換性のための古い挙動)であり、本実装の不具合ではない。この文字(U+00A5)自体をどのキー組み合わせでも入力できないことを確認したため、`type_text`では「¥」を非対応文字として明示的に拒否するようにした(黙って別の文字を送らない)。

### 5. マウス相対移動はOSのポインタ加速の影響を受ける

**症状**: `mouse_move`に`{x:200, y:0, absolute:false}`を送っても、実際のカーソル移動量は200pxちょうどにはならず、Windowsの「ポインタ精度を高める」等のポインタ加速(ballistics)設定の影響で移動量が拡大された。

**原因**: これはバグではなく、実物理マウスの相対移動と同じ経路(標準`MOUSE_INPUT_DATA`)でOSに渡しているため、OS側のポインタ加速カーブがそのまま適用される、想定通りの挙動。

**対応**: 修正せず、既知の挙動として記録。ピクセル単位で正確な位置決めが必要な場合は、相対移動ではなく絶対移動(`absolute:true`)の使用を推奨(ただし下記6も参照)。

### 6. マウス絶対移動の座標系(解明・対応済み)

**当初の混乱の経緯**: 初回セッション(デュアルモニタ)・後続セッション(シングルモニタ)のいずれでも、`absolute:true`で異なる正規化値を送っても着地点がほとんど変わらないという、絶対座標モードが機能していないように見える観測が続いた。ディスプレイ構成の変化(利用者の操作によらないデュアル→シングルモニタの切り替わり)と観測タイミングが重なったため、一時的に検証を保留していた。

**原因判明**: 実際の原因は座標マッピング自体ではなく、**カーソル位置を読み取っていたテストコード側の不備**だった。具体的には:

1. `System.Windows.Forms.Screen`/`Cursor.Position`は、呼び出し元プロセスのDPI認識設定に応じて座標を仮想化(スケーリング)して返す。DPI認識を明示的に設定していないプロセスでは、モニタごとの表示スケール(今回のセカンダリモニタは150%)に応じて座標が歪んで報告される
2. さらに、一部のPowerShellホストプロセスでは、`Screen`クラスがディスプレイ構成を初回アクセス時にキャッシュし、実行時のディスプレイ変更を反映しないケースがあった(セッション内で古い構成の数値が返り続けた)

`SetProcessDpiAwarenessContext(DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2)`を**そのプロセスで最初のグラフィックス関連API呼び出しより前に**呼び、かつ**毎回新しいプロセス**(`powershell.exe -NoProfile -File ...`)で読み取ることで、物理ピクセル座標を正確に取得できるようになった(`test/get_physical_cursor_pos.ps1`)。

**確定した変換式**: マルチモニタ環境(プライマリ 3440×1440 @150%、セカンダリ 1920×1080 @100%、`test/realworld_mouse_move_once.mjs`で1点ずつ送信・`get_physical_cursor_pos.ps1`で物理座標を都度確認)で、X/Y軸を分離した4点(`(0,32768)`, `(65535,32768)`, `(32768,0)`, `(32768,65535)`)を送信したところ、以下が完全に一致した:

```
物理X = round(正規化X / 65536 * プライマリモニタの幅)
物理Y = round(正規化Y / 65536 * プライマリモニタの高さ)
```

すなわち、**`absolute:true`の0-65535正規化座標は、常にプライマリモニタの物理ピクセル範囲(DPIスケーリング%とは無関係)にマッピングされる**。これは標準Win32 `SendInput`の`MOUSEEVENTF_ABSOLUTE`(`MOUSEEVENTF_VIRTUALDESK`を指定しない場合と同じ)の仕様と完全に一致する。同一の入力値は、送信前のカーソル位置によらず常に同じ物理座標に着地することも、異なる開始位置から確認済み(真の絶対座標であることの確認)。

**制限事項(既定動作、`virtualDesktop:true`で解除可能)**: この0-65535正規化方式は既定では**プライマリモニタの範囲しか表現できない**。セカンダリモニタなど、プライマリモニタの外側を対象にする場合は、下記の`virtualDesktop`オプションを使う(または相対移動を使う)。

**相対移動によるモニタ境界越えの確認(成功)**: 上記の「相対移動を使う必要がある」という代替案が実際に機能するかを検証した(`test/realworld_mouse_relative_sequence.mjs`)。プライマリ側の境界付近(物理`(1500,1400)`、`absolute:true`で設定)を起点に、`mouse_move({x:0,y:300,absolute:false})`を5回連続で送ったところ、最終的に物理`(1500,2519)`に到達した — これはセカンダリモニタの範囲(`y:[1440,2520]`)内であり、**プライマリからセカンダリへの越境が実際に成功したことを確認**した。続けて`{x:0,y:-300}`を5回送ると`(1500,869)`に戻り、**逆方向(セカンダリ→プライマリ)の越境も確認**した。11回の移動を通じてX座標は`1500`のまま完全に安定しており(送信していないX方向に動くことはない)、相対移動は物理マウスと同じくモニタをまたいで正常に機能する。

**検証方法上の注意点**: 当初、1回移動するたびに別プロセス(`powershell.exe`)を起動してカーソル位置を確認する手法を取ったところ、送信していないはずのX座標が毎回不規則に変化する(そのたびに違う値になる)という、一見バグのような現象が発生した。オペレーターが実際にマウス/トラックパッドに触れていないことを確認した上で、**複数回の移動を1つのプロセス・1つの接続内で連続実行し、最後に1回だけ位置確認する方式に変更したところ、この不規則な挙動は再現しなくなった**。原因は特定できていないが(繰り返しのプロセス起動自体が何らかの形でマウス状態に影響した可能性がある)、複数手順にまたがるマウス動作の検証では、外部プロセスの起動を挟まず一連の操作を1つのスクリプト内で完結させることを推奨する。

**追加で見つかった実バグとその修正**: 上記の変換式を確認した後も、`(29834,20526)`のような「キリの良くない」任意の値を単発で送ると、着地点が式と一致しない(しかも試行のたびに異なる、再現しない値になる)という現象が残っていた。一方、`(0,32768)`のような境界・中間値から始まる4点シーケンスは何度実行しても完全に再現した。切り分けた結果:

- **同一の値を2回連続で送ると、1回目は着地せず(または不定の位置になり)、2回目で必ず正確な位置に着地する**ことを確認した(例: `(0,0)`→`(40000,40000)`の順で送ると`(40000,40000)`が確実に正しく着地するが、`(40000,40000)`を単発で送ると不定になることがあった)
- これは、実物理の絶対入力デバイス(タッチパネル・タブレット等)によくある「最初の1サンプルはキャリブレーション用で、実際のカーソル移動には反映されない」という挙動と一致する。合成注入した`MOUSE_INPUT_DATA`(`MOUSE_MOVE_ABSOLUTE`)についても、mouclass側が同様の初回サンプル特別扱いをしている可能性が高い

**対応(実装済み)**: `src/tools.ts`の`mouse_move`ツールで、`absolute:true`の場合は同じ値を2回連続で書き込むように変更した(`MOUSE_EVENT_SETTLE_MS`の間隔を空けて)。修正後、`(29834,20526)`, `(40000,40000)`, `(10000,50000)`, `(60000,5000)`, `(1000,1000)`の5点全てで、変換式通りの物理座標(±1px、丸め誤差の範囲内)に確実に着地することを確認した。既に正しい位置にいる場合の再書き込みは無害(見た目上の変化がない)なので、この対応に副作用はない。

### `MOUSE_VIRTUAL_DESKTOP`フラグによる仮想デスクトップ全体への絶対移動(実装・確認済み)

[MSDNの`MOUSE_INPUT_DATA`リファレンス](https://learn.microsoft.com/ja-jp/windows/win32/api/ntddmou/ns-ntddmou-mouse_input_data)に、`Flags`のビットとして`MOUSE_MOVE_ABSOLUTE`(`0x0001`)とは別に**`MOUSE_VIRTUAL_DESKTOP`(`0x0002`)**——「マウス座標は仮想デスクトップにマップされる」——が定義されていることをユーザーから指摘された(本ドキュメントの以前の版では「セカンダリモニタには到達できない」と誤って断定していた)。

`helper/oib_bridge.c`に`OIB_MOUSE_VIRTUAL_DESKTOP = 0x0002`を追加し、`absolute`かつ`virtualDesktop`指定時は`Flags = MOUSE_MOVE_ABSOLUTE | MOUSE_VIRTUAL_DESKTOP`を送るように実装。実機(生JSON経由の直接テスト)で検証したところ、**正規化座標が仮想デスクトップ全体(今回の環境では物理`(0,0)`〜`(3440,2520)`)にマッピングされ、セカンダリモニタへ直接到達できることを確認した**(誤差は丸めの範囲内)。`src/tools.ts`/`src/bridge.ts`/`helper/oib_bridge.c`に配線し、`mouse_move`ツールに`virtualDesktop`パラメータ(既定`false`)として追加した。

**追加で見つかった「コールドスタート」の悪化**: `virtualDesktop`フラグを新たに導入して検証したところ、上記の「2回書き込みで確実に着地する」対応だけでは不十分なケースがあった。具体的には、`absolute`と`virtualDesktop`の組み合わせ(Flagsのビットパターン)を**初めて使う、または直前と異なるビットパターンに切り替えた直後**は、2回書き込んでもなお不正な位置(送信していない別の値になる)に着地することがあった。3回連続で書き込む(`MOUSE_EVENT_SETTLE_MS`の間隔を空けて計3回)ように変更したところ、複数回のコールドスタート条件(直前に`SetCursorPos`で無関係な位置にリセット、直前が異なるFlagsの組み合わせだった場合など)で全て1回の呼び出しで正確に着地することを確認した。

**「隙間」領域への着地に関する注記(バグではない)**: 仮想デスクトップの矩形境界(`(0,0)`〜`(3440,2520)`)の一部は、実際にはどのモニタにも対応しない「隙間」領域になる(モニタの物理的な配置が互い違いのため)。この隙間に対応する正規化座標を送ると、Windowsは最も近い実在モニタのピクセルへカーソル位置をクランプする(例: `(525,2307)`という隙間の座標を送ると、セカンダリモニタの左端`(761,2307)`にクランプされた)。これは想定通りの挙動であり、不具合ではない。`virtualDesktop:true`を使う際は、対象がどのモニタの実ピクセル範囲に収まるかを事前に確認することを推奨する。

## タイプ速度(自動化の価値の定量化)

上記のタイミング対策を踏まえた、現在の`type_text`のデフォルト設定での理論上のタイプ速度。

- Shiftなし文字1文字あたり: `TAP_HOLD_MS`(25ms) + `KEY_EVENT_SETTLE_MS`(30ms) + `delayMs`既定値(20ms) = **約75ms/文字**(実際のIPC往復時間を含めると80〜85ms程度)
  → **約12〜13文字/秒、1分あたり約700〜800文字**
- Shift付き文字(大文字・記号)1文字あたり: 上記に加えてShiftキーのdown/settle/up分(約85ms)が上乗せされ、**約160ms/文字**(約6〜7文字/秒)

人間の高速タイピング(概ね300〜500文字/分程度)と比べても遜色ない速度で、かつ疲労やタイプミスなく無人実行できる点が、`SendInput`/UI Automation等の既存手法にはない自動化の価値の一つである。速度が問題になる場面では`delayMs`パラメータで調整できるが、間隔を詰めすぎると上記3のShift取りこぼしリスクが上がるため、既定値をこのバランス(信頼性優先)にしている。

## 排他モードの実機検証結果(成功)

### 自動テスト(`watchdog_test.ps1`、物理操作不要)

- `enable_exclusive_input_mode`(`watchdogTimeoutMs=3000`)を送信後、**ハートビートを一切送らず**5秒待機
- 3秒経過後、ヘルパーの内部ウォッチドッグスレッドが自律的に`disable`を実行し、`{"event":"exclusive_mode_auto_disabled","reason":"heartbeat_timeout","failedDeviceCount":0}`を出力
- `failedDeviceCount:0` = 開いていた20個のコントロールデバイス全てでフィルタ/優先順位のリセットに成功
- その後の`heartbeat`照会で`exclusiveModeActive:false`を確認、明示的な`disable_exclusive_input_mode`も`wasActive:false`(既に非アクティブ)を正しく返す

**結論**: ウォッチドッグによる自動解除は実機で確実に機能する。

### 対話テスト(`realworld_exclusive_session.mjs`、ユーザーの物理キーボード操作を含む)

タイムスタンプ付きログと、実際にオペレーター(ユーザー本人)が各フェーズで物理キーボードを操作した結果:

1. **フェーズ1**: `enable_exclusive_input_mode`実行、合成テキスト`MARKER_BEFORE_`を送信 → 正常に着弾
2. **フェーズ2(20秒間、排他モード有効中)**: オペレーターが物理キーボードを操作 → **対象アプリ(Notepad)には一切反映されず**(この間に記録された内容は合成テキストのみで、物理入力の混入は皆無だった)
3. **フェーズ3**: 2つ目の合成テキスト`_MARKER_STILL_ACTIVE`を送信 → 正常に着弾(排他モードが継続して有効であることを確認)
4. **フェーズ4**: `disable_exclusive_input_mode`実行 → 正常終了
5. **フェーズ5(15秒間、排他モード解除後)**: オペレーターが物理キーボードを操作 → **今度は正常に反映された**(解除直後の合成テキスト送信と物理入力のタイミングが重なり内容は一部混在したが、物理キー入力が実際に画面に反映されることは明確に確認できた)

**結論**: 排他モードは実機で設計通りに機能する — 有効化中は物理入力を確実に遮断し、合成入力のみが対象アプリに届く。無効化すると物理入力は即座に復元される。ウォッチドッグによる自動解除も正常に機能する。

### プロセス強制終了によるエスケープハッチ(成功、`realworld_kill_escape_session.mjs`)

SECURITY.mdに記載した「`oib_bridge.exe`プロセスを終了させることが、唯一かつ確実な緊急解除手段」という主張を実機で検証した。

1. `enable_exclusive_input_mode`(`watchdogTimeoutMs=120000`)実行、合成テキスト`BEFORE_KILL_MARKER_`を送信 → 正常に着弾
2. 排他モード有効中(物理入力遮断状態)のまま、`Stop-Process -Force`で`oib_bridge.exe`を強制終了(`disable_exclusive_input_mode`は一度も呼び出していない)
3. プロセス終了直後、オペレーターが物理キーボードを操作 → **即座に対象アプリ(Notepad)へ反映された**

実際の記録内容: `BEFORE_KILL_MARKER_gggghyoooo` — 合成マーカーの直後に、キル後の物理キー入力がそのまま続いている。明示的な解除コマンドを一切経由せず、プロセスの強制終了だけでドライバ側のハンドルクローズ処理(WDFファイルクローズコールバック)がchainからの除外とキューの解放を行い、物理入力を即座に復元することを確認した。

**結論**: SECURITY.mdの「唯一の緊急解除手段」という主張は実機で裏付けられた。MCPサーバー・AIエージェントが完全に応答不能になった場合でも、`oib_bridge.exe`プロセスを終了させれば確実に物理入力が復元される。

なお、TypeScript側の`OibBridge`はヘルパープロセスの異常終了を検知すると次回のリクエストで自動的に新しいプロセスをspawnする仕様のため、キル直後に`get_exclusive_mode_status`を呼ぶと(新しいプロセスの初期状態である)`exclusiveModeActive:false`が返る。これは「古いプロセスの後片付けが機能した証拠」にはならない(新規プロセスは元々非アクティブ状態で起動するため)ので、今回の検証はUI Automationによる実際の入力内容の確認で行った。

## マウスクリックの座標精度検証(成功)

上記6の絶対座標修正後、`mouse_click`の実用上の精度を実際のUI要素で検証した(`test/realworld_mouse_move_once.mjs`・`realworld_mouse_click_once.mjs`、`get_tab_bounds.ps1`/`get_document_bounds.ps1`でUI Automationから物理座標を取得)。

1. Notepadに2つのタブ(`scratch_click_test_a.txt`が非選択、`scratch_click_test_b.txt`が選択中)を用意
2. `scratch_click_test_a.txt`タブのUI Automation上のバウンディング矩形から中心座標を計算し、正規化座標に変換
3. `mouse_move(absolute:true)` → `mouse_click(button:"left")` を実行
4. UI Automationで選択状態を確認 → **`scratch_click_test_a.txt`が選択状態に切り替わり、`scratch_click_test_b.txt`が非選択になったことを確認**(1回目の試行はテスト実行中にウィンドウ位置がずれて失敗したが、座標を取り直した2回目で正確に成功)

右クリック(コンテキストメニュー表示)・マウスホイールの上下スクロールもエラーなく実行できることを確認した。ただし、右クリックのコンテキストメニュー出現とホイールのスクロール位置変化は、モダンNotepadの当該UI要素がUI AutomationのMenu/ScrollPatternを公開していないため、自動検証はできなかった(実行時エラーが出ないことのみ確認)。

**追記(File Explorerでの追検証)**: 右クリックについては、File Explorer(`C:\Windows\System32`フォルダ)で再検証したところ、UI Automationの`ControlType.Menu`では検出できなかったものの、`EnumWindows`でウィンドウクラス`XamlExplorerHostIslandWindow_WASDK`(Windows 11のモダンなWinUI/XAMLベースのコンテキストメニュー)が実際に出現することを確認できた。**右クリックは正しくコンテキストメニューを開いている**が、Windows 11の新しいコンテキストメニュー実装はUI AutomationのMenuコントロールタイプとして公開されないため、そちらでの検出は今後も期待できない。

## マウスホイールのスクロール位置検証(成功)

File Explorer(`C:\Windows\System32\drivers`フォルダ、28項目・`ScrollPattern`公開済みのリストビュー)で、`mouse_wheel`が実際にスクロール位置を変化させることをUI Automationで確認した(`test/realworld_wheel_scroll_once.mjs`)。

1. カーソルをリスト中心へ移動(`absolute:true`)、`VerticalScrollPercent`が`0`であることを確認
2. `mouse_wheel({delta:-720})`(下方向6ノッチ分)を実行 — カーソル位置とホイール送信を1つのスクリプト内で連続実行(モニタまたぎ検証で得た教訓通り、別プロセスを挟むとカーソル位置がずれることがあったため)
3. `VerticalScrollPercent`が`0`→`3.21`に変化したことを確認 — **ホイールが実際にスクロールを引き起こしていることを客観的に確認**

なお、同じ内容を別プロセス(新規`oib_bridge.exe`)から追加でもう一度送信した際は値が変化しなかった。これは絶対座標移動で確認済みの「新規プロセスでの初回書き込みが不安定になることがある」現象と同種と考えられ、ホイール自体の機能不全ではないと判断している。

**結論**: `mouse_click`(前セクション)・`mouse_wheel`(本セクション)とも、実際のUI操作として機能することを実機で確認できた。右クリックのコンテキストメニュー出現も、ウィンドウクラス検出により確認済み(前セクション参照)。これでv1ツール一式の実機検証は一通り完了した。
